# 团队开发约定

## 负责范围

任务开始前确定负责人、模块 ID、可修改目录以及会调用的公共接口。每位成员可负责 1–3 项业务模块，各模块有独立的目录和生命周期。目录按工作类型划分：页面属于模块 `web/`，数据获取与业务 API 属于 `server/`，该模块的检查属于 `checks/`，说明属于模块自己的 `README.md`。同一模块可以同时包含前后端，它们仍放在各自的子目录内。

| 范围 | 修改边界 |
| --- | --- |
| 框架负责人 | `backend/main.py`、`backend/core/`、启动脚本、模块加载规范、全局配置、`checks/check_framework.py` |
| 公共 UI 负责人 | `web/`、`docs/DESIGN.md`；导航、公共组件、统一设置和主题 |
| 认证负责人 | `backend/services/auth/`、`backend/core/vault.py`、`scripts/`、认证检查及 `docs/AUTH.md` |
| AI 负责人 | `backend/services/ai/`、AI 检查及 `docs/AI.md` |
| 业务模块负责人 | 被分配的 `modules/<id>/`，包括自己的 `module.json`、前后端、检查和说明 |
| 集成人员 | 经协调确认的公共接口、依赖、锁定文件和跨模块连接；验证整体集成 |

业务成员需要新公共能力时，先提出所需接口及请求/响应示例，由对应负责人修改公共服务。不要在模块内复制登录、密码加密、AI HTTP 客户端、主题或全局设置。不要直接修改主框架、其他成员模块和公共依赖文件；只有任务负责人明确分配了相关范围才修改。由模块自己的公开接口提供协作能力，不导入其他模块的私有 Python、JS 文件，也不读取其用户数据目录或 SQLite 状态。

## 分支与 PR

团队建立 Git 仓库后，以主分支保存已集成的可运行状态，每人从最新主分支创建自己的功能分支，例如 `feat/mail-reader`、`feat/course-materials` 或 `fix/auth-expiry`。一个分支对应一个明确任务。开发过程中在自己的分支持续提交，把日常小改动保留在该分支。

功能达到可运行、可评审阶段后再创建 PR，例如一个完整的模块接入或一组相关修复。PR 写清功能变化、自己的修改范围、验证方法，以及确有必要的公共接口变化；避免为每个文件、每次样式微调创建独立 PR。保持分支与主分支同步，由各目录负责人处理所属代码的冲突；统一依赖和框架冲突交由集成人员处理。各成员只维护自己的分支，合并前由集成人员确认接口和整体启动状态。

## 最简代码标准

统一采用 Ponytail 风格：先阅读现有调用关系，复用已有组件和共享服务；优先标准库与已安装依赖，只写当前需求完整闭环所需的代码。明确输入和边界，不为假想场景堆叠包装、自动回退或重复配置。需求含糊且会改变接口或目录职责时，立即向任务负责人确认。

Python 遵循现有四空格缩进、类型与命名方式；浏览器代码采用 ES Modules、清楚的函数名和原生 DOM。公共 API 输入用 Pydantic 校验，模块自己校验源网站响应；错误响应使用可公开的信息，日志只记录必要的状态，不记录密码、Cookie、登录票据、密钥或原始私人响应。前端输出文字使用 `textContent` 或 `context.ui.escape`。

演示阶段验证可运行的实际路径即可。新增解析、状态分支、安全边界或生命周期时，留下一个小型断言检查；优先合成数据和模拟 HTTP。本人改动影响的接口说明与调用方随改动一起更新。调用外部付费 AI 或使用真实账户进行集成验证，应遵守该用户对数据和外部操作的授权范围。

## 开发流程

1. 明确自己的模块 ID、分类、负责目录和公共接口，阅读设计与模块文档。
2. 在自己的分支创建 `modules/<id>/`，填写模块清单和自己的说明文件。
3. 前端用注入上下文和公共组件，后端用 `context.auth`、`context.ai`、`context.store`、`context.secrets` 和 `context.data_dir`。
4. 启动网页，在设置中刷新模块，验证启用、页面切换、停用和再次启用。
5. 完成模块自己的小型检查，更新接口说明，再提交一个完整阶段的 PR。

主导航分类由框架统一提供；模块选择一个已有分类挂载。新增分类、全局设置项、公共组件或跨模块聚合能力由相关负责人确认并实施。公共契约以 `/api/v1` 和 `api_version: 1` 为当前版本，破坏性调整先由集成人员协调所有调用方。

## 环境、数据与桌面集成

Python 开发使用 WSL Ubuntu-26.04、uv 和当前项目 `.codex/venv`；用项目启动及检查脚本保持环境一致。临时数据、截图、登录验证窗口资料和缓存都放在本项目 `.codex/`。用户持久资料放在 `.private/`，账号、会话和 API Key 使用 Vault 加密。这两个目录以及环境文件遵循 `.gitignore`，分享项目时按代码文件清单交接。

当前以浏览器网页实现功能验证。Electron 由桌面负责人在模块集成后统一接入：应用窗口、标签页、系统浏览器和应用内链接策略由桌面层管理；模块通过框架提供的接口使用这些能力。网页模块维持原来的生命周期及 HTTP API，模块代码中不直接导入 Electron 或调用 Node.js 系统权限。

新增需要 AI 调用工具完成工作的功能，分配独立模块 ID，在该模块的 `harness/` 中实现原生 Cordis 插件，通过 `context.ai.run(..., plugins=[模块ID])` 调用官方运行时。框架维护凭据、运行时适配和生命周期，业务提示、工具、结果校验及界面由模块维护。插件使用标准 package.json 与官方接口；依赖和 bundle 配置随插件放在同一目录。基础文本处理使用共享 `generate`、`chat`。详细接入方式见 [AI 与插件文档](AI.md)。

模块代码是本地受信任代码，与框架运行在同一个用户权限下。目录及上下文隔离用于明确协作边界，安全能力由部署方式及代码审查共同保证。
