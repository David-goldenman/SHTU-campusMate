# 团队开发约定

## 负责范围

任务开始前确定负责人、模块 ID、可修改目录以及会调用的公共接口。每位成员可负责 1–3 项业务或 AI 插件模块，各模块有独立的目录和生命周期。页面属于模块 `web/`，数据获取与业务 API 属于 `server/`，原生 AI 工具及 bundle 属于 `harness/`，检查属于 `checks/`，说明属于模块自己的 `README.md`。一个模块按实际职责提供相应入口。

| 范围 | 修改边界 |
| --- | --- |
| 框架负责人 | `backend/main.py`、`backend/core/`、启动脚本、模块加载规范、全局配置、`checks/check_framework.py` |
| 公共 UI 负责人 | `web/`、`docs/DESIGN.md`；导航、公共组件、统一设置和主题 |
| 认证负责人 | `backend/services/auth/`、`backend/core/vault.py`、`scripts/`、认证检查及 `docs/AUTH.md` |
| AI 负责人 | `backend/services/ai/`、官方 SDK 版本和运行时适配、共享 AI 检查及 `docs/AI.md` |
| 业务与插件模块负责人 | 被分配的 `modules/<id>/`，包括清单、页面、Python API、原生插件、检查和说明 |
| 集成人员 | 经协调确认的公共接口、依赖、锁定文件和跨模块连接；验证整体集成 |

业务成员需要新公共能力时，先提出所需接口及请求/响应示例，由对应负责人修改公共服务。不要在模块内复制登录、密码加密、AI HTTP 客户端、主题或全局设置。不要直接修改主框架、其他成员模块和公共依赖文件；只有任务负责人明确分配了相关范围才修改。由模块自己的公开接口提供协作能力，不导入其他模块的私有 Python、JS 文件，也不读取其用户数据目录或 SQLite 状态。

## 分支与 PR

`main` 保存已集成的可运行状态。每项新任务从最新 `origin/main` 创建自己的功能分支，例如 `codex/mail-reader` 或 `codex/course-materials`。一个分支对应一个明确任务，开发中的提交保存在该分支。

功能达到可运行、可评审阶段后创建目标为 `main` 的 PR。PR 写清触发场景、最终行为、修改范围、验证结果和公共接口变化。提交前运行 `git fetch origin`，在功能分支整合 `origin/main`，检查 `git diff --stat origin/main...HEAD`。冲突按已文档化的接口和双方业务语义解决，验证最终提交。共享依赖与框架冲突由集成人员处理；AI 扩展以本文和 [AI 契约](AI.md) 为统一标准。PR 合并后，本地快进拉取 `main`，通过项目脚本更新环境并重启 demo。

## 最简代码标准

统一采用 Ponytail 风格：先阅读现有调用关系，复用已有组件和共享服务；优先标准库与已安装依赖，只写当前需求完整闭环所需的代码。明确输入和边界，不为假想场景堆叠包装、自动回退或重复配置。需求含糊且会改变接口或目录职责时，立即向任务负责人确认。

Python 遵循现有四空格缩进、类型与命名方式；浏览器代码采用 ES Modules、清楚的函数名和原生 DOM。公共 API 输入用 Pydantic 校验，模块自己校验源网站响应；错误响应使用可公开的信息，日志只记录必要的状态，不记录密码、Cookie、登录票据、密钥或原始私人响应。前端输出文字使用 `textContent` 或 `context.ui.escape`。

演示阶段验证可运行的实际路径即可。新增解析、状态分支、安全边界或生命周期时，留下一个小型断言检查；优先合成数据和模拟 HTTP。本人改动影响的接口说明与调用方随改动一起更新。调用外部付费 AI 或使用真实账户进行集成验证，应遵守该用户对数据和外部操作的授权范围。

## 开发流程

1. 阅读 README、本文、模块接口；涉及 AI 时阅读 AI 文档。明确模块 ID、分类、负责人、资料范围、工具副作用和使用的公共接口。
2. 从最新 `main` 建立功能分支。先写模块 README 中的请求、响应、错误状态与存储约定，再在 `modules/<id>/` 实现清单和所需入口。
3. 新增 AI 工具或工作流时，为该能力分配独立模块 ID，在 `harness/` 提供标准 npm 包、原生 Cordis 工具或 bundle。模块后端通过公开 API 选择资料，使用 `context.ai.run(..., plugins=[模块ID])`；基础文本处理使用共享 `chat`、`generate`。需要模型按需读取资料时，参考 `academic-assistant` 的任务令牌与本机工具路由，通过后端内部 `plugin_env` 配置插件；在页面与 README 说明资料及外部发送范围。
4. 校验模型结果、引用和账号版本，再由模块后端保存状态或执行对外写入。普通状态使用 `context.store`，秘密使用 `context.secrets`，持久文件使用 `context.data_dir`；前端继续使用注入的 API、组件和卸载信号。引用只接受本次实际读取的来源与连续原文；学习偏好依据用户明确提供的信息保存，学校要求保留来源，不从方案版本推断入学年份。
5. 在设置中刷新、启用、停用插件；检查页面切换与再次启用。新增工具验证一条真实运行时链路和必要的参数边界，使用合成资料与模拟模型。修改公共接口时同步修改调用方和对应文档。
6. 在 Windows 运行 `./check.ps1`，或在 WSL 运行 `bash ./check.sh`；有界面改动时检查实际操作。模块 README 记录所需服务、输入输出、数据与外部访问范围、清理方式和检查入口。
7. 同步主分支并解决冲突，确认 PR 差异只包含本任务；提交已验证的最终代码和文档，创建 PR。合并并拉取主分支后，重启本地网页确认模块就绪。

跨模块后台功能沿用上述流程：先声明事件来源、账号范围、资料变化判定、工具副作用与用户确认方式，再通过 `campus-agent` 的原生插件接入。只读能力由模块 OpenAPI 提供；写入使用明确的业务 API，不提供任意 POST、命令或文件权限。邮件语义分类由 `mail` 校验完整偏好、资料指纹与原文证据；通知通过 `notifications/imports` 汇入；日程通过 `timetable/events/import` 按稳定来源标识导入。新增自动写入必须说明依据和完成状态，并检查重复执行及手动修改保留。

首页会话管理、课程聚合、邮箱分栏与通知操作的改动，除本模块 Python 检查外，分别运行 `node modules/academic-assistant/checks/check_web.mjs`、`node checks/check_campus_workspace.mjs` 和 `node checks/check_ui_theme.mjs`。浏览器检查使用合成响应；截图保存在开发目录。版本升级时同时检查旧聊天迁移和重启恢复，避免用重置用户资料解决数据格式变化。

AI 接入方式按功能选择：

| 功能 | 入口与职责 |
| --- | --- |
| 单次文本生成、JSON 输出、显式消息对话 | 共享 `context.ai.generate`、`.chat`；模块选择输入并校验输出 |
| AI 调用工具、组合步骤并完成工作 | 独立模块的原生 Harness 插件，通过 `context.ai.run` 执行 |
| 插件配置与所依赖的 Cordis 服务组合 | 插件自己的 `package.json` 与 `dsh.bundle.patch` |
| 模型、Key、SDK 升级、宿主策略或共享接口 | 共享 AI 负责人维护，由集成人员验证调用方 |

业务导航分类由模块清单声明并由框架统一呈现；同一分类使用一致的导航元数据。全局设置项、公共组件或跨模块聚合能力由相关负责人确认并实施。公共契约以 `/api/v1` 和 `api_version: 1` 为当前版本，破坏性调整先由集成人员协调所有调用方。

## 环境、数据与桌面集成

Python 开发使用 uv；Windows 环境为 `.codex/windows-venv`，WSL 环境为 `.codex/venv`。应用默认 Windows 原生启动，也可通过 --distro / CAMPUS_WSL_DISTRO 选择 WSL。开发检查、截图和合成夹具保存在 `.codex/`；应用 Windows 环境为 `.private/runtime/windows/venv`，WSL 环境为 `.private/runtime/venv`。运行缓存、固定登录资料与 Harness 工作区在 `.private/runtime/` 管理。模块文件下载暂存在 `context.data_dir/tmp/downloads/`，传输结束删除。用户持久资料放在 `.private/`，账号、会话和 API Key 使用 Vault 加密，浏览器站点数据由 Edge 管理。私有目录和开发目录遵循 `.gitignore`。

依赖安装与检查使用 `uv sync --locked`。

四人协作继续按负责目录和公共接口分工：每个 PR 同步所影响的接口文档、调用方和检查；公共路径、依赖与启动入口由集成人员统一合入。源码目录、用户数据和生成环境分开交接，具体发布检查与迁移步骤见 [交付与移植规范](DELIVERY.md)。

当前以浏览器网页实现功能验证。Electron 由桌面负责人在模块集成后统一接入：应用窗口、标签页、系统浏览器和应用内链接策略由桌面层管理；模块通过框架提供的接口使用这些能力。网页模块维持原来的生命周期及 HTTP API，模块代码中不直接导入 Electron 或调用 Node.js 系统权限。

AI 工具和工作流统一使用官方 Harness 运行时及项目锁定的 SDK。模型连接、凭据和宿主生命周期集中在共享服务，业务能力集中在独立插件模块。接口的新增字段保持 `api_version: 1` 的兼容性；SDK 或契约升级需同时更新文档与原生插件检查。每次任务创建独立运行时与工作区，插件在当前工作区保存分析中间文件，任务结束自动清理，长期结果交给模块存储。

模型提供商通过共享 AI 设置选择，模块不固定模型服务域名或要求所有提供商必须保存 API Key。内置环境认证和自定义协议交给官方适配器，界面按当前提供商说明资料发送范围。目录升级与配置变更验证见 `checks/check_ai_providers.py`。邮件分类、文件夹和日／周总结由 `mail` 提供公开 API；跨模块使用这些结果时保留邮件 ID、日期范围和覆盖数量，不能把本地摘要当作完整历史邮箱。

模块代码是本地受信任代码，与框架运行在同一个用户权限下。目录及上下文隔离用于明确协作边界，安全能力由部署方式及代码审查共同保证。

## 集成与模块边界

四名成员从 main 建立短期功能分支；main 始终保留所有验收通过的功能。公共框架不枚举业务模块，不参与业务资料选择。模块清单声明导航，跨模块使用公开 API，依赖停用按文档降级。每个 PR 通过完整、独立、停用恢复、空框架四种模式验证，再由其他成员审阅；见 [AGENTS.md](../AGENTS.md) 与 [边界决策](architecture/0001-module-boundaries.md)。

## PR 自动检查

PR 提交与更新运行 `CI required`，完整检查入口与本地共用；新模块的 `checks/check_*.py` 自动加入。合并前由另一名写权限成员审核最新修改。当前分支保护的套餐限制、检查覆盖和故障处理见 [CI 约定](CI.md)。
