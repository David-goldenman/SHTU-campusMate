# 学习通知

通知中心汇总带来源的学习待办、邮件重点、服务故障和活动建议，保留已读状态。学习通知与 Piazza 分页显示，每条通知先显示标题、来源、时间和简短预览，展开查看完整 Markdown、原文与提醒依据。未读点、标题粗细和信封操作表达阅读状态，打开详情保留原有已读状态。“整理设置”提供后台助手启停、检查及学习待办生成；活动详情展示时间、地点与原文依据，可明确“参加并加入时间表”或“不参加”。确认后显示时间表入口，参加确认与原站报名分别处理。顶部常驻铃铛由独立的 `campus-agent` 模块提供。

默认查看未读通知，已读和全部历史可切换查看。布置、截止或待提交提醒仅引用明确对应的作业，且全部关联作业的最新可靠记录均已提交时，自动标为已读，保留 `auto_read` 的原因、时间与作业 ID。成绩、批改和反馈通知保留未读。草稿、未知、读取失败或旧缓存不会触发处理；混合其他来源的通知保留给用户核对。曾自动处理的通知遇到明确未提交或草稿会重新显示，用户手动设置的已读／未读优先。检测通过作业管理公开 `/snapshot` 完成，读取通知及后台每 30 秒核对，不调用 AI，也不修改学校通知或原邮件。

`POST /imports` 接收 `{account_revision,id,title,summary,source_revision,importance?,why?,citations?,proposal_id?,event_at?}`，按当前账号及稳定 ID 更新；账号不一致返回 409。每条 citation 为 `{id,title,source,url}`，importance 为 `urgent/important/normal`。相同资料保留已读，资料版本更新恢复未读；导入通知最多保留最近 300 条，原有提炼结果单独保留。

`GET /agent/status`、`PUT /agent/settings {enabled}`、`POST /agent/check` 通过公开 API 代理后台助手；缺失时保留本模块的通知显示。`POST /proposals/{id}/accept|dismiss` 代理明确参加／拒绝动作，错误状态沿用来源接口。后台普通写入使用框架保护，任务工具使用各自模块的短期令牌。

通过课程中心公开 API 和共享 AI 提炼本学期课程的重要事项；邮件提醒统一使用邮箱分类及校园后台助手的导入结果。`GET /snapshot` 读取通知、错误与资料范围；`POST /generate?force=false` 生成，相同资料与上海日期复用已有结果，force=true 重新分析。每条通知必须引用实际所选资料，来源 URL 由缓存提供；格式、日期或引用错误保留上次结果并返回 502。

读取通知及后台检查会通过 `mail/intelligence` 与 `campus-agent/proposals` 核对当前分类、复核进度和参加选择。已筛选、一般通知、等待新偏好复核，以及已拒绝活动的提醒，从可见列表收起；记录和阅读状态仍保存在当前账号的数据中。分类重新有效后按当前状态显示。历史通用生成器引用邮件的结果由邮箱专用链路管理；新的通用生成只选择课程等其他资料。源模块停用时保留已存状态。

`PUT /{notice_id}/read {read:true}` 更新已读。通知 ID 由标题与来源组成；相同来源内容保留已读，来源文字更新后恢复未读。`GET/PUT /settings {auto_generate:true}` 控制自动提炼，默认关闭。开启且共享 AI 已配置时，后台每 30 秒检查资料变化；仅变化时调用模型。模块停用会唤醒并等待后台任务结束，已发出的模型请求沿用共享服务的超时限制。

通知与错误按账号版本隔离，普通状态保存在本模块 Store。项目 `check.sh` 使用合成模型结果验证去重、已读状态、引用、失败缓存与后台清理。

资料范围经课程中心公开 `POST /context` 获取；课程中心停用或缺失返回 409 提示，模块自身仍可加载、停用与恢复，已有历史按账号隔离保留。

跨模块 `/imports` 支持可选 `active`（默认 true）；来源撤销时以相同稳定 ID 和新来源版本提交 `active:false`，记录保留但不展示、不计未读。群消息由其来源模块管理提醒，通知 AI 不重复分类。

用户明确标记“无需我提交”的作业也可消除对应截止/待提交通知，auto_read.reason=assignment_not_required，保留原站状态。只有全部关联作业已可靠提交或本地无需提交才处理；混合待办、成绩/反馈及手动已读/未读保持不变。恢复本地选择后，相应未完成提醒重新出现。

活动过期独立于参加建议和 AI 自动生成。通过 mail /intelligence 的可信 event_window（或非邮件已核实 proposal）补齐旧通知的 expiry:{at,basis,source_ids} 与活动时间。全部关联活动必须有可靠窗口，使用最晚失效时间；日期未知、混合其他事项、成绩反馈、问卷、补交补签和仍可提交的作业不因 event_at 过期而消失。不能只用通知发布时间或原始 event_at 自动清理。

读取通知和后台约每 30 秒执行时钟检查，即使 AI 暂停或依赖暂不可用，也能按已保存的活动窗口归入已读，保留 auto_read.reason=event_expired 和过期时间；不删除原始通知、不修改原邮件和时间表。快照提供 expired，前端历史显示原因，已过期或已开始的建议不再显示参加按钮。用户手动已读／未读优先。来源改期到未来或有效时间证据被撤回时，只有自动处理的提醒会重开；重启和重复导入保留同版本处理状态。

check_expiry.py 覆盖无内容变化的时钟触发、保留历史、改期、手动状态、多来源、离线与账号切换；mail/checks/check_event_window.py 验证依据与换行日期。
